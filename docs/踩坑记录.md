## A. 框架选型坑

### A1. BepInEx 稳定版没有 IL2CPP 包 ⛔

- **坑**：直觉是"用 GitHub 最新稳定版"（当时 5.4.23.5），但 5.x 全系 release 资产里**只有 Mono 构建**
  （`BepInEx_win_x64_*.zip`），IL2CPP 包历史上从来没进过稳定版 release——对 IL2CPP 游戏物理不可用。
  用 Mono 包硬上 = 游戏原样启动（doorstop 链路对不上）。
- **规则**：
  - IL2CPP 游戏 → 只看 `builds.bepinex.dev` 的 bleeding-edge 构建；
  - **Unity 6 游戏必须 be.753 之后的构建**（PR #1284，2026-03-07 合入 IL2CPP metadata v23-106 支持；
    be.753 及更早启动 Unity 6 游戏直接 `Failed to generate Il2Cpp interop assemblies` 后退出，issue #1266）；
  - 判断当前游戏是否 Unity 6：读 `UnityPlayer.dll` 的 ProductVersion（本游戏 6000.2.0a1）。

### A2. HarmonyX native detour 在 Unity 6000.2.0a1 上必闪退 ⛔⛔（最大坑）

- **症状**：插件加载正常（日志停在 `Chainloader startup complete`），游戏跑到**主界面 WebUI 初始化阶段**
  无声退出。Player.log 无异常、无 Windows 崩溃事件、无 Unity crash dump——像被"正常关闭"，极易误判为用户手关。
- **实测二分**：BepInEx 无插件 ✅ 稳定；插件加载但不挂 patch ✅ 稳定；挂 **1 个** patch ❌ 必崩；挂 6 个 ❌ 必崩。
  与 patch 的目标、参数形态无关（`object[] __args` 注入、`Vector2Int` struct 返回值 marshal 都是高危路径，
  但去掉它们也不行——detour 机制本身在这个 Unity alpha 版上不稳）。
- **根因**：HarmonyX 给 IL2CPP 方法装的原生跳板（trampoline）与 Unity 6000.2.0a1 运行时不兼容，
  安装时或首次调用时原生层损坏。
- **规则**：
  - **这台游戏（Unity 6000.2.0a1）禁止一切 Harmony patch**。需要"hook 游戏逻辑"时，用
    **注入 MonoBehaviour 主线程轮询 + interop 直改数据**的零钩子方案（插件 ConfigPoller 的模式）；
  - 判断"是不是 detour 崩"：闪退 + 无任何日志/崩溃记录 + 死在固定的初始化阶段 → 八成是它；
  - 验证手段：把 patch 全部注释（保留插件壳）跑二分，别靠猜。

### A3. "闪退"也可能是优雅退出，先取证据再定论

- 一次进程消失实际是用户自己关了窗口（Player.log 末尾是 Physics/Input System 的**正常关停序列**）；
  另一次才是真 detour 崩溃。两者日志特征几乎一样，容易互相污染判断。
- **规则**：判崩溃看三件套——`Player.log` 末尾是否有"Shutdown"序列（=正常退出）、
  Windows 事件查看器有没有 EventID 1000/1001、有没有 crash dump 目录。都有其一才算 crash。

## B. 插件运行时坑

### B1. BepInEx 会回写它托管的 cfg 文件，与外部写入打架 ⛔

- **症状**：GameTrainerBox 把 `Overrides = 7:9:11,1001:12:8` 写进 BepInEx cfg，插件检测到变化并应用配置，
  但读到的值**永远是空**；日志连续 `cfg reloaded: overrides=''`。事后看文件：键行变回 `Overrides = `（空），
  数据成了孤立行。
- **根因**：插件的 `ApplyParsed` 设置 `ConfigEntry.Value` 会触发 **BepInEx 用内存态重写整个 cfg 文件**，
  外部（GameTrainerBox）刚写入的内容被拆行/清空——两个写方打架，BepInEx 总是最后赢。
- **规则**：
  - **游戏行为控制的数据绝不放 BepInEx 托管的 cfg**——用独立文件（本例 `*.overrides.txt`），
    插件自己监视 mtime；BepInEx cfg 里只放"往返无损"的简单标量（bool 的 EnableResize 实测无损）；
  - 诊断特征记住：**日志里 cfg reloaded 多次且值全是空 = 有第二个写方在打架**。

### B2. BepInEx 6 BE 没有 ThreadingHelper，主线程调度用注入 MonoBehaviour

- BepInEx 5 IL2CPP 时代的 `ThreadingHelper` 在 6 BE 里不存在（全 core 目录 grep 无此类）。
- **规则**：需要主线程执行 interop 调用时，`ClassInjector.RegisterTypeInIl2Cpp<T>()` 注入
  MonoBehaviour（记得写 `IntPtr` 构造函数，否则运行时报错），挂到 DontDestroyOnLoad 的空 GameObject 上，
  在 `Update()` 里干活（本插件 3 秒一拍）。

### B3. 部署插件 = 拷 DLL，游戏运行时文件被锁

- **症状**：`cp` 报 `Device or resource busy`。
- **规则**：部署守望用"直接重试拷贝直到成功"的循环（`until cp ...; sleep 20`），
  **不要**用"检测进程退出再拷"——tasklist|grep 偶发漏检会让守望提前退出（实测踩过）。

## C. 游戏更新 / 内存定位坑

### C1. 游戏小版本更新就会让 TypeInfo RVA 失效 ⛔

- 1.0.15690 → 1.0.15704（约 5MB 的补丁），`Attr_TypeInfo` 槽位从 `0x538bef0` 挪到 `0x538bf00`。
- **症状分层**（都见过）：
  - 旧 RVA 指向被复用的槽位 → 读到**合法但对齐的别的对象指针**（实测指向一个 String 对象）→
    klass 校验通过但字典验证全挂 → 报"签名扫描+遍历均失败"；
  - script.json 的 Address → 非对齐魔数 → 报"Attr 类尚未初始化"（假象！用户明明在局内）。
- **规则**：
  - **script.json 的 ScriptMetadata.Address 在 1.0.15704 实测与运行时槽位差 8~24 字节，不可再用**
    （旧版能用，更新后失效——工具会漂移，别信文档上"永远如此"的流程）；
  - 用 `scripts/locate-attr-class.ts` 内存定位（见 C2），profile 更新后冒烟验证。

### C2. 别对 Il2CppClass 内存布局做假设 ⛔

- 定位脚本最初假设 `Il2CppClass+0x10 = name 指针、+0x18 = namespace 指针`，在 Unity 6.2 alpha 上读出来的
  是垃圾（+0x10 是 int、+0x14 起是内联 UTF-16 "enviro..."——那根本是个 String 托管对象）；
  想在 GameAssembly 模块里搜类名字符串也失败——**IL2CPP 的类名/命名空间字符串在 metadata 堆
  （私有 RW 内存）里，不在 DLL 模块内**。
- **规则**（locate-attr-class.ts 的现行算法，版本无关）：
  1. 堆搜命名空间字符串 → 2. 堆搜指向它的 8 字节指针（= Il2CppClass 候选）→
  3. 不做结构假设，**从 Attr 对象头 `[obj+0]` 读 klass 指针投票**（同 class 多对象全票一致）→
  4. 回 GameAssembly 模块反搜该指针得到候选槽位 → 5. 逐个候选用完整扫描器自动验证。
- 顺带：EnvBox/UnlockBox 不是容器（只是地图区域标记）；字符串字面量不在模块内。

### C3. 同形字典一大堆：模板 / 镜像 / 邻居 / 主角 ⛔

- **症状**：定位/扫描"成功"了，读出来的数值全是错的（生命=100、饱食度=0，而游戏 HUD 是 467/295）。
- **根因**：堆里同时存在多个 klass 相同、键集相同的 98 项字典（实测本局 3 个）：
  - **模板**：base 值恰好等于键值（键 1→1、键 2→2...），上限=键+100；
  - **邻居等实体**：默认上限（100/100/100/90/100），数值也随游戏实时变化（会骗过"只看是否变化"的鉴别）；
  - **主角**：上限被养成/修改器拉高（实测上限总分 2109 vs 邻居 490），数值连续消耗。
  另有 **22 项的 GameKey 假字典**：entry 签名兼容、值是一致的其他类——klass 错误时它能蒙混
  `validateDict`（它自己的一致性），读出"GameKey_10"这类字符串数据。
- **规则**（已实装进引擎 `scanner.ts`，按顺序）：
  1. 模板过滤（排序后前 5 个 entry 的 base==键值特征）；
  2. 3 秒动态采样——活实体的饱食度/体力连续消耗必然变化，静止的剔除；
  3. 采样无区分度时（全变/全不变，比如游戏暂停）按**上限总分**排序兜底——主角被养成/修改器拉升；
  4. 无区分度时**不写缓存**（cache v2 版本号，结构变更自动失效），日志提示游玩中重扫；
  5. `validateDict` 的 klass 校验是最后的闸门，但记住：**klass 错误时假字典可能反而蒙混，真字典被拒**。
- 诊断工具：`scripts/diag-dicts.ts` 枚举全部候选字典并打印五维值 + value 对象原始字节。

## D. 工程与工具链坑

### D1. 脚本打包的陈旧 bundle 会把诊断带偏 ⛔

- **症状**：给冒烟脚本加了新鉴别逻辑，跑起来行为完全没变，反复"验证"旧结论，浪费大量排查时间。
- **根因**：`scripts/*.ts` 是用 `pnpm dlx esbuild` 现打包的 `.cjs`——**改了源码没重新打包，node 跑的还是
  旧 bundle**；且旧 bundle 是旧版引擎（连异步签名都对不上时居然还能跑通旧逻辑）。
- **规则**：改了 `engine/` 或 `scripts/` 后跑诊断，**必须显式重建 bundle**；建议在脚本输出里带一行
  版本/时间戳，一眼识别陈旧产物。

### D2. 把顶层代码包进 async main 时别用"首尾拼接"

- 用字符串拼接 `async function main() {` + 原文件 + `}` 的方式给脚本包异步，结果 **import 语句被裹进了
  函数体**——esbuild 直接语法报错（`Unexpected "{"`），而报错被 `/dev/null` 吞掉后链路继续跑旧产物。
- **规则**：包异步 = 重排文件结构（import 留在顶部，函数体只包执行代码）；esbuild 的 stderr 别静默。

### D3. shell 链式命令里的退出码陷阱

- `pnpm typecheck | grep -cE "error"`：**打印 0 但退出码是 1**（grep 无匹配）→ 后续 `&&` 步骤全部静默跳过，
  看起来"0 错误、一切正常"，实际构建/部署根本没执行。反过来 `cmd | tail -1` 的退出码永远是 tail 的，
  失败被吞。
- **规则**：关键步骤（typecheck/build/部署）单独跑、单独看输出；管道取输出时用 `;` 分隔后续命令，
  或对退出码显式判断。本轮至少两次被这个坑拖慢。

### D4. 后台守望/重试循环要防"误判退出"

- "检测进程退出再拷贝"的守望脚本，`tasklist | grep` 偶发一次漏检就提前退出（还带着失败的重试拷贝）。
- **规则**：重试型守望直接对**目标动作本身**做循环（`until cp ...; do sleep 20; done`），
  动作成功即退出，不依赖前置探测。

## E. 产品/交互坑

### E1. 别把程序内部数据暴露给用户

- 白名单让用户手填容器 ID（`1001,1003`）——用户根本不知道 ID 是什么。正确做法：插件导出容器清单
  （含游戏本地化名 `Name_Local`，"普通背包/野外登山包/购物车..."），UI 表格按名称勾选。
- 同名多行问题：普通背包在游戏内有**三次扩容等级**（8x8→8x9→8x10），每级一条 Config_Bag，
  名字相同——必须给名称加尺寸后缀区分，并提供"只看正在使用"过滤。

### E2. "正在使用"需要活实例检测，不能靠配置表

- 配置表里的条目多数是未使用的模板/历史等级。判活用游戏自己的数据层：
  `ReduxUISystem.Instance.reduxStoreLayer.dataTree` 里的 `State_Data_Item.BagCache`
  （ownerId → bagConfigId）就是局内活容器的权威集合。
- 兜底：没有任何 in-use 标记时（主界面/数据层未就绪）回退显示全量，别让列表变空白。

### E3. 弹性布局里塞卡片会把尾部内容挤没

- 训练页根容器是 `flex flex-col overflow-hidden`，加一张卡片后日志区（flex-1）被压缩到不可见。
- **规则**：内容会增长的页面用页面级滚动（根容器 `overflow-y-auto`），日志/终端类区域给**固定高度**
  内部滚动，不参与弹性分配。

## F. 一分钟检查清单（动这块代码前过一遍）

1. 游戏是否刚更新过？→ 先跑 `scripts/locate-attr-class.ts` 重定位 RVA，再谈别的
2. 插件要 hook 游戏方法？→ **不行**，改轮询 + interop 直改数据
3. 要往 BepInEx cfg 写非 bool 数据？→ **不行**，开独立文件
4. 冒烟/诊断脚本结果可疑？→ 先确认 bundle 是不是刚重建的
5. 读数不对？→ `diag-dicts.ts` 看是不是挑错了字典（模板/邻居/主角三选一）
6. 部署失败？→ 游戏没关（DLL 锁），挂重试循环
7. 数值看起来像模板/别人？→ 上限总分 + 动态采样鉴别链是否都被跳过了（缓存/单候选路径）
