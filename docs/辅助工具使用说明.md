# 辅助工具使用说明（活文档）

> 修改器（GameTrainerBox 属性引擎）与容器扩容 Mod 开发所需的**全部辅助工具的使用说明**：
> Il2CppDumper、BepInEx、dotnet SDK、诊断/定位脚本、插件构建部署，以及它们依赖的游戏知识与红线。
> **工具用法/路径/版本变更时同步更新本文与"最后更新"日期**；坑的来龙去脉见「踩坑记录」，
> 功能面见「修改器功能说明」「容器扩容Mod说明」。
> 最后更新：2026-09-05（2026-09-05 建立）
> 配套阅读：`CLAUDE.md`（架构约定、硬性规则与游戏文件位置）、`踩坑记录.md`（坑与规则来源）。

## 0. 这份文档管什么

覆盖两类开发共用的辅助工具与知识：

- **修改器侧**：属性字典重定位、扫描诊断、引擎冒烟（Il2CppDumper + GameTrainerBox scripts）
- **Mod 侧**：BepInEx 安装、插件构建部署、配置协议、容器系统知识

一句话背景（容器扩容原理）：游戏背包/所有容器的格子数由配置 `Config_Bag.Size`（`List<int>`，`[列, 行]`）
驱动，WebUI 按 `gridCols * gridRows` 动态渲染——**改数据即改 UI，不需要动任何 UI 文件**。
插件在主线程轮询改写该配置，GameTrainerBox 修改器通过直写插件配置文件实现界面控制。

```powershell

dotnet build -c Release
cp bin/Release/net6.0/SLContainerExpand.dll "<游戏目录>/BepInEx/plugins/"
```

## 2. 为什么是 BepInEx 6 BE（关键决策，勿回退）

- 游戏：Survival Log **1.0.15704**，Unity **6000.2.0a1**（Unity 6.2 alpha），IL2CPP（metadata v31）
- BepInEx **5.x 全系稳定版（含 5.4.23.5）只发布 Mono 构建，从未有 IL2CPP 包**（GitHub API 全资产核实过）——对本游戏物理不可用
- IL2CPP 构建只通过 bleeding-edge 渠道发布（官方文档明确）
- Unity 6 的 IL2CPP 支持是 2026-03-07 合入 master 的 PR #1284（"IL2CPP metadata v23-106 (Unity 6+)"）；
  **be.753 及更早的构建启动 Unity 6 游戏会报 `Failed to generate Il2Cpp interop assemblies` 后退出**（issue #1266）
- 因此用 **be.788**（2026-09-01 构建，含 #1284）。实测：interop 生成成功、游戏正常启动
- BepInEx 升级/重装步骤：下载对应 zip 解压覆盖游戏根目录 → 删除 `BepInEx\interop` 与 `BepInEx\unity-libs`（强制重新生成）→ 启动一次游戏

## 3. ⛔ 红线清单（细节与案例见「踩坑记录」A2/B/C3 与 CLAUDE.md 硬性规则）

1. 禁止 Harmony/HarmonyX patch 游戏方法（native detour 必闪退）——一律轮询 + interop 直改数据
2. 只扩不缩：缩小目标/换更小模式必须重启游戏还原
3. 不改 WebUI 静态文件（`WebUiInjectedMessage` 检测）
4. 反作弊联网上报（Sentry）：从配置源头修改保持全链路一致；永不直接改物品坐标或 ViewModel 格子数

## 4. 游戏容器系统知识（来自 dump.cs，已实测）

- **统一模型**：玩家背包、家具容器（储物箱/冰箱/抽屉）、无人机包全是 `BagComponent`
  （持 `BagConfigId`）→ 查 `Config_Bag`（`IConfig<int>`：`ID`、`Name`、`Size: List<int>`（`[列,行]`）、`Burden`）。
  `EnvBox`/`UnlockBox` 只是地图区域标记，不是容器。
- **实测配置样例**（1.0.15704）：背包 1-4 号 8x7→14x10（升级链）；家具容器 1001-1050、5xxx、115xxx
  约 5x3~10x14；仓库类 2001=16x12。全库 73+ 个配置。
- **数据流**：`Config_Bag.Size` → `SurvivalPlanningComponent.GetBagSize/GetGridChainMaxSize`（扩容链，
  游戏自带"购买扩容"机制 `ApplyBagGridExpansion`）→ `ItemManager.GetOwnerBagSize/GetLoadRepairBagSize`
  → `State_Web_BackpackUI`（ReduxUI）的 `GridCols/GridRows`（`ReactiveProperty<int>`，`[WebBind_Int]` 推给 WebUI）
  → `UI\BackpackUI\BackpackUI.html` 按 `gridCols * gridRows` 动态渲染格子（`webui-bag.js` 按 cols/rows 算 CSS grid）。
- 配置本体打包在 `SurvivalLog_Data\data.unity3d`（不可直接改文件），运行时由 `ConfigManager`
  （`BaseSingleton<ConfigManager>`，`_Config_Bag_Dict: Dictionary<int, Config_Bag>`）持有。

## 5. 插件 SLContainerExpand（v0.8）

源码 `<工具目录>\SLMods\ContainerExpand\Plugin.cs`（未随本仓库发布）。机制：

- `BasePlugin.Load`（`BepInEx.Unity.IL2CPP` 命名空间）里 `ClassInjector.RegisterTypeInIl2Cpp<ConfigPoller>`
  注入 MonoBehaviour 挂到 DontDestroyOnLoad 的 GameObject 上——**这是 BepInEx 6 BE 没有 ThreadingHelper 时
  做"主线程每帧工作"的标准姿势**（interop 调用必须在主线程）。
- `Update` 每 3 秒：①监视 cfg（EnableResize）与 `overrides.txt`（每容器绝对目标 `id:列:行`）两个文件的
  mtime 热重载；②遍历 `ConfigManager.Instance._Config_Bag_Dict`，按 Overrides 原地写
  `Config_Bag.Size`。纯 interop 调用，**零 native hook**。
- 幂等/纠偏（`BagInfo`：会话原始值 + LastTarget）：当前值==原始值 → 应用目标；==LastTarget（目标变了）→
  按原始值重算；都不是 → 判定游戏重载配置 → 重记原始值。只扩不缩：目标小于原始值直接跳过。
- 日志前缀 `SL Container Expand`，全部进 `BepInEx\LogOutput.log`（含首次发现的配置清单、每次应用、
  每次配置重载），排查先看这里。

配置（插件 3 秒内热应用；**两个文件**）：

| 文件 | 内容 | 说明 |
|---|---|---|
| `...containerexpand.cfg`（BepInEx 托管） | `EnableResize` = bool | 总开关 |
| `...containerexpand.overrides.txt`（独立文件） | `id:列:行` 逗号分隔，如 `7:20:16,1001:12:8` | 每容器**绝对目标**格子数；未列出的容器保持原始大小 |

⚠️ **Overrides 不能放 BepInEx cfg 里**：插件应用配置会触发 BepInEx 回写 cfg，把外部写入的值
拆行/清空（v0.7 实测踩坑——cfg reloaded 四次 overrides 全为空）。布尔值 EnableResize 来回写无损，可留在 cfg。

旧版（≤v0.5）的 `Mode/ColMultiplier/RowMultiplier/ColAdd/RowAdd/BagIdWhitelist` 已废弃，v0.8+ 插件解析时忽略。
容器清单 JSON（`com.gametrainerbox.survivallog.containerexpand.containers.json`，与 cfg 同目录）由插件在游戏内导出：
`{updatedAt, containers:[{id, name, local, cols, rows, origCols, origRows}]}`，GameTrainerBox 的
`trainer.listContainers` 读取它渲染选择表格（用户按中文名勾选/填写目标格子，无需知道 ID）。

  （只看正在使用/筛选）+ 应用

## 7. 常见任务速查

- **游戏更新后扫描/Mod 全挂**：①重新 dump（§1 命令）刷新 dump.cs/script.json/DummyDll →
  ②**用 `scripts/locate-attr-class.ts` 在局内定位新 Attr_TypeInfo 槽位**（klass 无关签名扫描 →
  稀有键 81012 等过滤假字典 → value 对象头投票得 klass → 模块反搜 klass 指针 → 逐个 RVA 完整扫描自动验证）→
  ③把输出的 RVA 更新进 profile `attrTypeInfoRva` → ④若 GameAssembly 大改，关游戏删
  `BepInEx\interop`/`unity-libs` 重启生成 → ⑤GameTrainerBox 重新扫描。
  ⚠️ **script.json 的 ScriptMetadata.Address 在 1.0.15704 实测与运行时槽位差 8~24 字节，不可直接使用**
  （1.0.15690 时代可以，更新后失效；已实测 0x538bf08 vs 运行时 0x538bf00）。
  已核实：Attr 字段偏移 0x10/0x14/0x18/0x1C/0x20/0x24 不变、AttrName 枚举 99 值不变、容器类全在
- **属性数据错误排查**：堆里可能同时存在 主角/邻居/快照/模板 多个同 klass 同键集的 98 项字典
  （实测：模板 base==键值；主角上限总分 2109（被养成/修改器拉升）；邻居 490 默认值）。
  引擎鉴别链 = 模板过滤 → 3 秒动态采样（活实体数值连续变化）→ 上限总分排序兜底；
  无区分度时不写缓存（cache v2），提示游玩中重扫。
- **扫描失败排查**：`scripts/diag-rva.ts`（读槽位原始值；非对齐魔数=没进存档，0xCC 填充=地址错）。
  `scripts/diag-dicts.ts`（枚举全部签名命中的候选字典+value 原始字节——曾借此发现 22 项 GameKey 假字典
  与 98 项真字典并存）。`scripts/wait-scan.ts`（轮询等进存档自动扫描）。
  已知陷阱：正确 klass 下 `validateDict` 会过滤假字典；klass 错时假字典反而可能蒙混（它自己的一致 klass）
- **运行冒烟**：`pnpm dlx esbuild scripts/smoke-engine.ts --bundle --platform=node --external:koffi --outfile=scripts/.smoke-engine.cjs && node scripts/.smoke-engine.cjs`（需在游戏局内）。
- **改小某容器的格子**：清空该容器条目（写空 overrides）→ 重启游戏还原 → 再设新值（只扩不缩保护）。
- **验证 Mod 生效**：看 `BepInEx\LogOutput.log` 的 `Config_Bag[x] Size AxB -> CxD` 行。
