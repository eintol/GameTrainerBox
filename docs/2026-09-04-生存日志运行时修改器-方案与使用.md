# 生存日志(Survival Log) 运行时属性修改器 - 方案与使用

日期: 2026-09-04
状态: 已完成并实测验证（属性修改实时生效, 游戏 UI 同步刷新; 修改可随存档持久化, v1.1 修复上限硬封顶问题）

## 一、需求

游戏运行过程中实时修改主角属性（生命/饱食度/士气/体力等），不做离线存档编辑。

## 二、成果

修改器位于游戏安装目录下的 `SaveEditor\`：

| 文件 | 说明 |
|---|---|
| `启动修改器.bat` | 双击启动 GUI（pythonw 无控制台窗口） |
| `trainer.py` | GUI 主程序：扫描 / 修改五维与上限 / 锁定 / 金钱(值扫描定位) |
| `memproc.py` | 进程内存引擎（纯 ctypes，零依赖；进程/模块/区域枚举、读写原语） |
| `scanner.py` | 主角属性字典定位器（类指针特征扫描 + Dictionary entries 遍历） |
| `cli_scan.py` | 命令行版定位工具（调试用） |
| `..\Tools\Il2CppDumper\` | IL2CPP dump 工具与当前版本的 dump.cs / script.json（网上下载的辅助工具统一放游戏目录 `Tools\` 下） |
| `extract_schema.py` / `mpack.py` / `save_schema.py` / `verify_parse.py` | 存档(MemoryPack)解析器，本路线未启用，留作备用 |

游戏本体: Unity IL2CPP (GameAssembly.dll, metadata v31, 版本 1.0.15690)。
进程: `SurvivalLog.exe`。运行环境: Python 3.14。

## 三、使用方法

1. 启动游戏，**进入存档局内**（主界面时属性类未初始化，扫描会提示）。
2. 双击 `启动修改器.bat`，点"扫描属性"（全堆扫描约 10~30 秒）。
3. 表格里按**游戏显示值**填写新值 → "应用修改"；点"上限→500"按钮把该属性上限一键拉满到游戏硬封顶 500（自动按强化值折算 base 并保持 Max 封顶字段）。
4. 勾选"锁定"后每 0.3 秒自动写回，游戏逻辑改不掉。
5. 金钱（可选）：在交易界面看数字，填入"游戏内金钱"点"定位"，再填新值点"修改"。

**持久化（改动想保留到下次启动）**：改完后在游戏里正常存档一次（过天/手动保存/结算）再退出。
游戏存档时会把内存值写回存档文件（`AttributeComponent.SaveGame`），重启后改动保留；未存档就强退则改动丢失。

## 四、实测确认的关键事实

- **属性容器**: 运行时主角属性在 `AttributeComponent.AttrDict`（`Dictionary<AttrName, Attr>`，共 98 项）。
- **IL2CPP Dictionary Entry 布局**（AttrName 枚举键 → 引用值）:
  `[hashCode(4)][next(4)][key(4)][pad(4)][value指针(8)]`，共 24 字节；int 枚举键的 hashCode == key。
- **Attr 对象布局**: 头 16 字节(Il2CppObject) + `BaseValue(0x10, int)` + `StrengtheningValue(0x14)` + `ConditionValue(0x18)` + `Max(0x1C)` + `Min(0x20)` + `isSingle(0x24, bool)`。
- **单位换算**: 五维当前值的游戏显示 = BaseValue / 1000（如 60000 → 60.0）；上限显示 = base + 强化值。
- **UI 键映射**: 游戏 UI 的"生命"条 = 键 5 (Vitality)；键 4 (Health) 界面无对应条（隐藏健康值）。
  五维: 1 饱食度 / 2 士气 / 3 体力 / 4 Health / 5 生命(Vitality)；101-105 为对应上限。
- **修改生效**: 直接写 BaseValue，游戏 UI 在下一次属性同步(回合/结算/属性变动)时刷新显示；实测改动即时反映到界面。
- **上限硬封顶（v1.1 确认）**: `Attr.Max`(0x1C) 字段（五维实测 = 500）是游戏对上限的硬封顶，游戏 UI 把上限显示/计算 clamp 在该值。
  上限 = `base + 强化值`（修改器口径）。v1.2 起 GUI 取消了自由的上限输入框，改为每行一个"上限→500"按钮：点击后按 `base = 500 - 强化值` 折算写入，正好拉满到硬封顶，并同时保证 `Max` 字段不低于 500。
  （v1.1 曾允许任意上限值，因游戏 clamp 在 500 造成"修改器显示 1045、游戏显示 500"的困惑，已按用户要求简化。）
- **持久化（用户实测）**: 改内存后正常存档退出（`SaveGame` 写回存档）→ 重启后上限/数值不回退；未存档强退则丢失。
  运行时改 + 触发一次存档 ≈ 等价于改存档，且不碰序列化格式、无校验风险。

## 五、定位原理（为什么稳定）

不硬编码任何游戏对象地址，仅一个版本相关的入口：

1. `GameAssembly.dll` 基址 + `ATTR_TYPEINFO_RVA`(0x538bef0) 读出 `Attr` 的 `Il2CppClass*`。
   （该位置在类未使用时是 IL2CPP 的未初始化魔数，进局后才是真指针——扫描器有明确报错。）
2. **慢路径（首次，实测约 4 秒）**: 一遍全堆签名扫描——Dictionary entry 的 `hashCode==key` 且 `pad` 恒为 0，
   用「key + 4字节零」8 字节签名直接 find（键序 105→104→5→1 依次尝试），命中后双向遍历 entries 数组
   （一次大块读取，非逐项系统调用）得到 key→Attr 对象全表。
3. **校验**: 主角字典形似（键 1-5 与 101-105 齐全）+ 项数下限 30 + klass 指针抽样校验（防陈旧/复用内存）。
4. **快路径（之后，实测约 0.2 秒）**: 成功锚点缓存于 `SaveEditor\attr_cache.json`，重扫直接重走 entries 数组；
   映射每次从活动内存重新推导（不缓存映射），无陈旧风险；游戏重启/重进存档后校验失败自动落回慢路径并刷新缓存。

外部进程 Read/WriteProcessMemory，不注入、不调用游戏 API，不会触发游戏内的 API 级作弊检测字段（`_confirmedCheatKeys` 等只监控游戏内部调用）。

## 六、游戏更新后的维护

大版本更新若扫描报"Attr 类尚未初始化/版本可能已更新"：

1. `cd Tools\Il2CppDumper`（dump 工具在游戏目录 `Tools\` 下，与修改器代码分离）
2. `Il2CppDumper.exe "..\..\GameAssembly.dll" "..\..\SurvivalLog_Data\il2cpp_data\Metadata\global-metadata.dat" .`
3. 在新生成的 `script.json` 里搜 `GameCore.HotUpdate.Battle.Logic.Attr_TypeInfo`，取其 Address（十六进制）。
4. 更新 `scanner.py` 顶部的 `ATTR_TYPEINFO_RVA`。

其余逻辑（堆扫描、字典遍历、Attr 偏移、单位换算）不依赖版本。

## 七、已知限制

- 属性修改的 UI 显示刷新是事件驱动（下个回合/属性变动时），逻辑值立即生效。
- 锁定原理是高频写回，不是冻结分配；Boehm GC 不移动对象，同局内地址稳定。重进存档/重启游戏后地址变化，
  扫描器通过 klass 抽样校验自动检测并落回慢路径重新定位（缓存自动失效刷新），无需手动干预。
- 扫描性能（实测）: 首次全堆签名扫描约 4 秒；之后走锚点缓存约 0.2 秒。
- 金钱定位为一次性值扫描（值改变后需重新定位），未实测（游戏主界面无金钱显示，用户确认不需要）。
- `MPack` 存档解析路线中 `DynamicEventArgsSave` 的成员数校验未通过（dump 字段顺序与 MemoryPack 序列化序存在差异），该路线未完成，不影响运行时修改器。
